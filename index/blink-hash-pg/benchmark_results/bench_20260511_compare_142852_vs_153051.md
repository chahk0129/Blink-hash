# Benchmark Comparison: WAL metadata fix

Compared runs:

- Baseline: `bench_20260511_142852.txt`
- After improvement rerun: `bench_20260511_153051.txt`

Both runs used the same `scale=1000` time-series workload and completed the same visible benchmark sections:

1. Load 1000 monotonic rows
2. Build the `ts` index
3. Point lookup on 1,000 random `ts = X` queries

## Summary

The WAL metadata fix is a correctness change, not a throughput optimization, so the benchmark does not expose a large expected speedup. The two completed runs are effectively equivalent for the visible benchmark path; the small timing differences are within normal run-to-run noise.

## Measured Deltas

| Metric | Baseline | After improvement | Delta |
| --- | ---: | ---: | ---: |
| `idx_blinkhash_ts` build time | 74 ms | 79 ms | +5 ms |
| `idx_btree_ts` build time | 74 ms | 70 ms | -4 ms |
| Blink-hash point lookup `Execution Time` | 0.033 ms | 0.038 ms | +0.005 ms |
| Btree point lookup `Execution Time` | 0.074 ms | 0.036 ms | -0.038 ms |

## Interpretation

- The query plans are unchanged between the two runs.
- The measured differences are tiny and should be treated as noise at this workload size.
- The real gain from the improvement is that WAL replay can now target the correct node/bucket, which is a correctness fix rather than a benchmark-visible performance change.

## Notes

- Early runs in this folder failed because of PostgreSQL environment issues or an existing database session, so they are excluded from the comparison.
- For a stronger performance comparison, rerun this same workload several times and average the results, or use a larger scale to reduce measurement noise.
